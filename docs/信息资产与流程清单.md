# 信息资产与流程清单

> 版本：v3
> 目的：穷举我们系统里的每一种信息和每一条流程，并说明**为什么它们必须被管理**

---

## 第一部分：我们的信息资产

### 核心原则

企业管理任何信息的前提是：**这条信息如果不被系统管理，会出什么问题？**

---

|-------------|---------|---------|

| 无法联系员工 | 紧急情况联系不到人，不知道找谁汇报 | BairesDev (2025)：Employee Database 是"primary source feeding IAM, payroll, expense management" |
| 组织混乱、不知谁向谁汇报 | 员工不知道上级是谁，审批流找不到审批人 | Oberoi (2024)：Job Analysis & Design 在战术层支撑培训需求和岗位评估 |
| 人员流失没有记录 | 无法追溯谁在什么时候做过什么岗位 | 飞书 People：员工全生命周期数据管理 |
| 紧急情况联系不到家属 | 员工突发状况，HR 翻纸质档案 | 安全管理基本要求 |

**一句话**：员工信息是所有 HR 业务的**基础数据**——没有它，招聘、发薪、考勤、审批全部无法落地。

**一句话**：组织架构是企业的**骨架**——没有它，员工不知道自己在哪、向谁汇报、跟谁协作。

## 第二部分：我们的流程

### 核心原则

一条流程必须被系统管理的条件是：**人工处理的成本 > 系统处理的风险**。

---

### P1. 员工全生命周期流程

#### 流程概览

```
员工入职
  → 录入基本信息（姓名/工号/部门/岗位/上级）
    → 写入履历（初始岗位分配）
      → 在职期间可变更信息（调岗/晋升/更新资料）
        → 离职/退休（状态变更，履历归档）
```

#### 为什么必须系统管理

| 人工处理的成本 | 系统处理的价值 | 学术支撑 |
|---------------|---------------|---------|
| HR 需要手动登记纸质档案，每次更新需翻找文件 | 集中的员工数据库，一次录入永久可用 | Ogunbanwo 2025 "Employee and department management" |
| 员工调岗后，纸质档案和实际部门脱节 | 数据库外键自动关联部门/岗位，职责清晰 | 钉钉/飞书：组织架构随人员变动实时同步 |
| 离职员工档案丢失，后续背调无法追溯 | job_history 完整记录每一次岗位变动 | 飞书 People "员工全生命周期" |

**不管理这个流程的最大风险**：**员工信息变成"死数据"**——入职时填什么就是什么，永远不更新，最终和现实完全脱节。

---

### P2. 组织架构管理流程

#### 流程概览

```
创建部门/岗位
  → 设定编码/职级/编制/负责人
    → 关联上下级部门
      → 分配员工到对应岗位
        → 可调整（合并/拆分/撤销）
```

#### 为什么必须系统管理

| 人工处理的成本 | 系统处理的价值 | 学术支撑 |
|---------------|---------------|---------|
| 组织调整靠口头通知，1个月后还有人用旧部门名 | 系统内统一更新，所有人看到的都是最新版本 | Conway's Law：组织架构决定沟通结构——混乱的组织导致混乱的协作 |
| 编制控制靠 HR 脑记，超编了也不知道 | headcount 字段直接比对人数的 SQL 查询 | Oberoi 2024 "HR Planning, maintain steady workforce" |

**不管理这个流程的最大风险**：**组织架构和实际运作"两张皮"**——系统里的部门表和实际的人员归属对不上。

---

### P3. 请假审批流程

#### 流程概览

```
员工提交请假申请
  → 系统记录提交内容（类型/时间/原因）
    → 审批人收到待办（pending状态）
      → 批准：更新状态为approved，记录审批人和时间
      → 驳回：更新状态为rejected，填写驳回意见
        → 流程结束，记录在案
```

#### 为什么必须系统管理

| 人工处理的成本 | 系统处理的价值 | 学术支撑 |
|---------------|---------------|---------|
| 员工给 HR 发微信请假，HR 忘了 → 算旷工 | 系统自动记录，谁批的、什么时候批的一清二楚 | Petchara 2025 "Technological Integration to enhance efficiency" |
| 纸质的请假条容易丢 | 数据库持久存储，永久可查 | SOC2 / 合规审计要求可追溯记录 |
| 管理者不知道团队谁在休假 | 审批人一看就知道谁提交了、谁在休假 | BairesDev 2025 "Event-driven architecture for real-time triggers" |

**不管理这个流程的最大风险**：**请假无据可查**——员工说请了，HR 说没批，最终变成劳资纠纷。

---

### P4. 角色与权限管理流程

#### 流程概览

```
定义角色（ADMIN/HR/EMPLOYEE）
  → 为角色分配权限（什么角色能干什么）
    → 创建用户
      → 为用户分配角色
        → 用户登录 → 系统鉴权 → 执行操作
```

#### 为什么必须系统管理

| 人工处理的成本 | 系统处理的价值 | 学术支撑 |
|---------------|---------------|---------|
| 所有用户共享同一个账号，出事找不到责任人 | 每人独立账号+密码哈希存储，安全可追溯 | Ogunbanwo 2025 "RBAC for security" |
| 用户权限靠口头传达，实际没有技术限制 | 路由级鉴权，无权限的操作直接被拦截 | Petchara 2025 "Data Management and Security" |
| 离职人员账号无法回收 | 账号状态控制，禁用后无法登录 | SOC2 / GDPR 合规要求 |

**不管理这个流程的最大风险**：**系统没有安全边界**——任何人可以做任何事，出了事找不到人负责。

---

### P5. 操作审计流程

#### 流程概览

```
每次增/删/改操作
  → 自动记录：谁 + 做了什么 + 对什么做的 + 什么时候
    → 写入 audit_log 表
      → 管理者可查询审计日志
```

#### 为什么必须系统管理

| 人工处理的成本 | 系统处理的价值 | 学术支撑 |
|---------------|---------------|---------|
| 没有日志，找不到谁删了数据 | 每个操作都有记录，可追溯到用户 | BairesDev 2025 "Automated, tamper-resistant logs for every meaningful interaction" |
| 出了安全问题靠猜 | 审计日志直接定位异常操作 | Petchara 2025：审计是"全面人事管理"的组成部分 |

**不管理这个流程的最大风险**：**出了事只能认栽**——不知道谁干的、不知道什么时候干的、不知道影响了什么。

## 第三部分：信息与流程的关系矩阵

```
                  ┌─── 员工信息 ───┐
                  │                │
            ┌─────┤  组织架构信息   ├─────┐
            │     │                │     │
            │     └───────┬────────┘     │
            │             │              │
            ▼             ▼              ▼
        ┌───────┐   ┌──────────┐   ┌──────────┐
        │ 请假   │   │ 职务基准  │   │ 办公地点  │
        │ 申请   │   │ 信息      │   │ 信息      │
        └───┬───┘   └────┬─────┘   └────┬─────┘
            │            │              │
            ▼            ▼              ▼
        ┌─────────────────────────────────────┐
        │         履历变更信息                  │
        │  (每一次调动/晋升/转岗都记录在案)      │
        └─────────────────────────────────────┘

        ┌─────────────────────────────────────┐
        │         用户与权限信息                │
        │  (所有上述信息的安全边界)              │
        └─────────────────────────────────────┘

        ┌─────────────────────────────────────┐
        │         审计日志                     │
        │  (所有上述操作的不可篡改记录)          │
        └─────────────────────────────────────┘
```

**核心逻辑**：

1. 员工信息 + 组织架构信息是**基础数据**——没有它们，一切无从谈起
2. 请假申请 + 履历变更是**业务数据**——它们描述了"发生了什么"
3. 职务基准 + 办公地点是**参考数据**——它们为标准和管理提供依据
4. 用户权限是**安全边界**——保护以上所有数据不被滥用
5. 审计日志是**最后一道防线**——出了问题有据可查

---

## 第四部分：结论

### 我们的系统管理了什么

**9 类信息 × 5 条流程**，构成了一个完整的最小 HRMS 闭环：

```
信息（What you have）→ 流程（What you do）→ 记录（What happened）
```

每一类信息和每一条流程的必要性，都可以用三句话回答：

| 问题 | 答案模板 |
|------|---------|
| 这是什么 | 定义信息/流程的类型和内容 |
| 不管理会怎样 | 具体到可感知的负面后果 |
| 学术怎么说 | 引用论文/工程实践支撑 |

**这就是老师要的"从需求到代码的完整思维链"——不是"我做了一个员工管理功能"，而是"因为企业不管理员工信息会导致组织混乱，所以我们设计了 employee 表，实现了 CRUD，并在此基础上扩展了 V3/V4 字段来覆盖更完整的员工画像"。**
